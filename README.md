# OGRSA — Online Grievance Redressal System Awareness

> **An educational Community Engagement Project (CEP)** built by a BSc IT student.
> OGRSA is **not** an official government portal and is **not** integrated with any
> government system. All statistics shown are generated by this application.

A complete, production-style full-stack web application that spreads awareness
about online grievance redressal systems **and** provides a fully working
platform where citizens can submit, track and manage grievances, and
administrators can process them through a transparent, auditable workflow.

---

## 1. Problem Statement

Many citizens are unaware that public-service complaints can be filed and
tracked online. Offline complaint mechanisms are opaque: there is no receipt,
no visibility of progress, and no accountability. OGRSA addresses this by
(a) teaching citizens how online grievance redressal works, and
(b) letting them experience the entire workflow hands-on.

## 2. Objectives

1. Spread awareness about online grievance redressal systems
2. Promote digital literacy and citizen participation
3. Demonstrate transparent grievance submission and tracking
4. Demonstrate a complete resolution workflow with feedback & accountability
5. Serve as a technically complete full-stack reference project

## 3. Features

**Citizen**
- Sign up / sign in / sign out via **Neon Auth** (no passwords stored by the app)
- Profile management (name, mobile; role is read-only)
- Submit grievances with category, priority, location, department and up to 3 attachments (PDF/JPG/PNG ≤ 5 MB)
- Unique public reference IDs (`OGRSA-2026-000001`) generated by a PostgreSQL sequence
- Personal dashboard with live statistics and charts
- List/search/filter/paginate own grievances
- Full grievance detail: description, attachments, status timeline, official remarks
- Add additional information while a grievance is open
- Public tracking by reference ID (privacy-safe, no login required)
- In-app notifications with unread badge, mark-as-read / mark-all
- Post-resolution feedback (1–5 stars + comment, one per grievance)

**Admin**
- Role-protected admin console (role lives in the application profile, never client-controlled)
- Dashboard with real aggregate analytics (status/category distribution, monthly trend, resolution rate, average resolution time, average rating)
- All-grievance list with search, status/category/priority/date filters, sorting and pagination
- Full grievance detail incl. citizen contact info and attachments
- Status updates through an enforced state machine (`SUBMITTED → UNDER_REVIEW → ASSIGNED → IN_PROGRESS → RESOLVED/REJECTED`), transactional with history + notification
- Remarks (notify the citizen), department assignment, rejection with mandatory reason
- Category management (create/edit/activate/deactivate — never hard-delete)
- Awareness content management (tips & FAQs shown on the public site)
- Feedback statistics
- CSV export (no private citizen data)

**Platform**
- Fully responsive (mobile → desktop), dark/light/system theme (persisted)
- Skeleton loaders, empty states, accessible forms/labels/focus states
- Centralized error handling with safe messages, rate limiting, Helmet, CORS

## 5. Architecture

```
Browser (React SPA)
   │  sign-up / sign-in / session / JWT ────────► Neon Auth (managed, neon_auth schema)
   │
   │  /api/* with  Authorization: Bearer <JWT>
   ▼
Vite dev proxy ──► Express API (validates JWT against NEON_AUTH_JWKS_URL)
                        │
                        ▼
                Drizzle ORM ──► Neon PostgreSQL (application tables, public schema)
```

- **Identity** is owned by Neon Auth (`neon_auth` schema — never modified by the app).
- The backend derives the user **only** from the validated JWT `sub` claim.
  `req.body.userId` is never trusted.
- Application data references the auth user via `profiles.auth_user_id`.

## 7. Neon Setup (exactly as used)

```bash
npm i -g neon@latest
neon login                       # or: NEON_API_KEY / neon profile create
neon skills -y                   # requires Node >= 22; installs agent skills/docs
neon mcp -y                      # installs the Neon MCP server for coding agents
neon link --project-id rough-water-22652449 --branch production -y
neon config init                 # creates neon.ts
# edit neon.ts -> auth: true
neon deploy                      # applies config; Neon Auth provisioned
neon neon-auth status            # verify Base URL + JWKS URL
```

`neon link`/`neon deploy` write the environment to `.env.local`:

```
DATABASE_URL=            # pooled connection (app runtime)
DATABASE_URL_UNPOOLED=   # direct connection (migrations)
NEON_BRANCH=production
NEON_AUTH_BASE_URL=      # Managed Better Auth endpoint for this branch
NEON_AUTH_JWKS_URL=      # JWKS endpoint for backend JWT verification
```

Frontend public variable (in `client/.env`):

```
VITE_NEON_AUTH_URL=<NEON_AUTH_BASE_URL>   # public login endpoint, safe for browsers
```

> Browser origins must be trusted by Neon Auth. `localhost` is pre-approved;
> add deployed origins with `neon neon-auth domain add https://your-app.example`.

## 10. Authentication Flow

1. React calls `authClient.signUp.email()` / `signIn.email()` (`@neondatabase/auth`
   with `BetterAuthReactAdapter`). Neon Auth manages credentials, sessions and cookies.
2. For API calls, the client obtains a **short-lived EdDSA JWT** via
   `authClient.token()` (cached in memory, auto-refreshed before expiry).
3. Axios sends it as `Authorization: Bearer <jwt>`.
4. Express verifies the token with `jose` against `NEON_AUTH_JWKS_URL`
   (issuer/audience = the Neon Auth host). No custom signing, no bcrypt.
5. The middleware loads (or lazily creates) the application profile keyed by the
   JWT `sub` claim and attaches it to the request. All queries are scoped to it.

## 11. Database Schema (public schema — application data)

- `profiles` — id (uuid PK), **auth_user_id (unique)**, name, email, mobile,
  role (`CITIZEN`/`ADMIN` enum), timestamps
- `categories` — id, name (unique), description, active, timestamps
- `grievances` — id, **reference_id (unique)**, user_id → profiles, category_id →
  categories, subject, description, location, department, priority enum, status
  enum, assigned_to → profiles, resolved_at, timestamps; CHECK constraints on
  subject/description length; indexes on user_id, category_id, status, priority,
  created_at
- `status_history` — id, grievance_id → grievances (cascade), status, remark,
  updated_by → profiles, created_at
- `notifications` — id, user_id → profiles (cascade), grievance_id, title,
  message, is_read, created_at; composite index (user_id, is_read)
- `feedback` — id, grievance_id (**unique** → duplicate prevention), user_id,
  rating (CHECK 1–5), comment, created_at
- `attachments` — id, grievance_id (cascade), file_name, storage_key, mime_type,
  file_size (CHECK ≤ 5 MB), uploaded_at
- `awareness_content` — id, section (TIP/FAQ), title, body, display_order, active
- `grievance_ref_seq` — PostgreSQL sequence backing public reference IDs

The `neon_auth` schema (users, sessions, accounts…) is **managed by Neon Auth**
and is never modified by this application.

## 12. Security

- ✅ Neon Auth for all authentication; **no passwords stored**, no bcrypt, no custom JWT signing
- ✅ Backend JWT validation (JWKS, issuer + audience pinned)
- ✅ Identity derived only from the validated token — never from request bodies
- ✅ Ownership enforced in SQL (`WHERE user_id = authenticatedProfileId`) → IDOR returns 404
- ✅ Role-based authorization middleware; **no self-promotion endpoint** (admin via trusted script only; role stripped from profile updates)
- ✅ Zod input validation on body/query/params; Drizzle parameterized queries
- ✅ Upload hardening: MIME + extension allow-list (PDF/JPG/PNG), 5 MB cap, random filenames, no executables
- ✅ Helmet, CORS allow-list, rate limiting (general + sensitive + public tracking anti-enumeration)
- ✅ Centralized error handler — no stack traces/DB errors/secrets in responses
- ✅ Secrets only in `.env.local` (gitignored); frontend receives only the public auth URL
- ✅ CSV export excludes private citizen data and guards against formula injection
- ✅ Public tracking exposes only safe fields (no remarks, names or contact data)

## 14. File Storage Strategy

Local development stores files in `server/uploads/` with randomized names, and
metadata in PostgreSQL. For production, swap the Multer disk storage for an
object store (Neon Object Storage / S3-compatible): store the object key in
`attachments.storage_key` and serve via short-lived signed URLs. Binary data is
intentionally kept out of PostgreSQL.

## 15. Known Limitations

- Single admin tier (no department-level sub-roles)
- English-only UI
- Public stats reflect only this application's data (by design — no fabricated government statistics)
